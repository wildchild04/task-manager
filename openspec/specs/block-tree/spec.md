## Requirements
### Requirement: Block identity
Every block SHALL have a string ID that is unique across the workspace and never changes for the lifetime of the block. IDs SHALL be generated by the caller that creates the block, so a client can reference a new block before it is persisted.

#### Scenario: ID is kept across changes
- **WHEN** a block is updated, moved, or has its type changed
- **THEN** its ID is unchanged

#### Scenario: Duplicate ID is rejected
- **WHEN** an insert uses an ID that already belongs to a block
- **THEN** the operation is rejected with a duplicate-ID error

### Requirement: Block types
A block's type SHALL be one of: `page`, `paragraph`, `heading`, `todo`, `bulleted_list_item`, `numbered_list_item`, `toggle`, `quote`, `divider`, `reference`, `comment`. Each type SHALL define a schema for its props, and props that do not match the schema SHALL be rejected. Type-specific props are:
- `heading`: `level` of 1, 2 or 3
- `todo`: `checked` boolean
- `reference`: `targetId` (see the block-references capability)
- all other types, including `comment`: no props

#### Scenario: Valid props are accepted
- **WHEN** a `heading` block is inserted with `{ level: 2 }`
- **THEN** the block is stored with those props

#### Scenario: Invalid props are rejected
- **WHEN** a `heading` block is inserted with `{ level: 4 }`
- **THEN** the operation is rejected with a validation error naming the invalid prop

#### Scenario: Unknown type is rejected
- **WHEN** a block is inserted with type `kanban`
- **THEN** the operation is rejected with a validation error

### Requirement: Rich-text content
Text-bearing types (`page`, `paragraph`, `heading`, `todo`, `bulleted_list_item`, `numbered_list_item`, `toggle`, `quote`) SHALL store content as an ordered list of text spans, each with a `text` string and an optional set of marks (`bold`, `italic`, `underline`, `strikethrough`, `code`, `link` with an `href`). For a `page`, the content is its title. `divider`, `reference` and `comment` blocks SHALL have no content.

#### Scenario: Content round-trips unchanged
- **WHEN** a paragraph is stored with spans `[{ text: "Hello " }, { text: "world", marks: ["bold"] }]`
- **THEN** reading the block returns exactly those spans

#### Scenario: Content on a non-text type is rejected
- **WHEN** a `divider` is inserted with non-empty content
- **THEN** the operation is rejected with a validation error

### Requirement: Ownership tree
Every block SHALL have exactly one owner. For most blocks the owner is its parent block (`parentId`). A block without a parent is a root, and only `page` and `comment` blocks MAY be roots. There are two kinds of root:
- a **workspace root page**: a root `page` with no owner entity, listed among the workspace's root pages
- an **owned root**: a root whose owner is an entity outside the block tree, given as `owner` (an entity kind and ID), for example a task's body page, a project's home page, or a comment's body

A `comment` block SHALL always be an owned root. The block layer SHALL store `owner` as given and SHALL NOT interpret it; the owning domain validates it. `owner` SHALL be set only at insert and SHALL never change, and an owned root SHALL NOT be moved. A block's parent SHALL exist. `divider` and `reference` blocks SHALL NOT have children. The ownership relation SHALL never contain a cycle.

#### Scenario: Non-page block without a parent is rejected
- **WHEN** a `paragraph` is inserted with no parent
- **THEN** the operation is rejected

#### Scenario: Comment block cannot be nested
- **WHEN** a `comment` block is inserted or moved under another block
- **THEN** the operation is rejected

#### Scenario: Comment must be owned
- **WHEN** a `comment` block is inserted as a root without an `owner`
- **THEN** the operation is rejected

#### Scenario: Owned page root
- **WHEN** a `page` is inserted as a root with owner `task:T1`
- **THEN** it is stored as an owned root and is not one of the workspace's root pages

#### Scenario: Owned root cannot be moved
- **WHEN** a move targets an owned root
- **THEN** the operation is rejected

#### Scenario: Parent must exist
- **WHEN** a block is inserted under a parent ID that does not exist
- **THEN** the operation is rejected with a not-found error

#### Scenario: Leaf types cannot have children
- **WHEN** a block is inserted or moved under a `divider`
- **THEN** the operation is rejected

### Requirement: Sibling order
The children of a parent, and the set of workspace root pages, SHALL have a single, total order. Owned roots SHALL NOT be part of any sibling order; their own children are ordered normally. Inserting or moving a block SHALL place it either first among its siblings or directly after a named sibling. Reading the children of a parent SHALL return them in that order.

#### Scenario: Insert first
- **WHEN** a block is inserted under a parent with children `[A, B]` and no "after" sibling
- **THEN** the children are `[new, A, B]`

#### Scenario: Insert after a sibling
- **WHEN** a block is inserted under a parent with children `[A, B]` after `A`
- **THEN** the children are `[A, new, B]`

#### Scenario: "After" block must be a sibling
- **WHEN** an insert or move names an "after" block that is not a child of the target parent
- **THEN** the operation is rejected

### Requirement: Operations
Blocks SHALL change only through four operations:
- `insert(block, parentId, afterId?)`, or `insert(block, { owner })` for an owned root
- `update(id, { type?, props?, content? })`
- `move(id, parentId, afterId?)`
- `delete(id)`

`update` SHALL NOT change a block's parent or position. Changing `type` ("turn into") SHALL keep the block's content and children, and SHALL replace its props with the new type's props given in the same update (or the new type's defaults). Changing between a text-bearing type and a non-text type, and changing to or from `comment`, SHALL be rejected.

#### Scenario: Turn a paragraph into a todo
- **WHEN** a paragraph with content "Buy milk" is updated to type `todo`
- **THEN** the block is a `todo` with content "Buy milk", `checked: false`, and the same children

#### Scenario: Turn a paragraph into a divider is rejected
- **WHEN** a paragraph is updated to type `divider`
- **THEN** the operation is rejected

#### Scenario: Move within the same parent
- **WHEN** `C` is moved after `A` in children `[A, B, C]`
- **THEN** the children are `[A, C, B]`

#### Scenario: Move to another parent keeps the subtree
- **WHEN** a toggle with children is moved under another page
- **THEN** the toggle and all its descendants appear under the new page, in the same internal order

#### Scenario: Move into own descendant is rejected
- **WHEN** a block is moved under one of its own descendants
- **THEN** the operation is rejected and nothing changes

#### Scenario: Delete removes the subtree and closes the gap
- **WHEN** `B` (which has children) is deleted from children `[A, B, C]`
- **THEN** the children are `[A, C]` and `B`'s descendants no longer exist

### Requirement: Atomic batches
Operations SHALL be applied as a batch of one or more operations. A batch SHALL either apply completely or not at all. Later operations in a batch SHALL see the effects of earlier ones. When a batch is rejected, the error SHALL identify the index of the failing operation and the reason.

#### Scenario: Split a block in one batch
- **WHEN** a batch updates block `A`'s content and inserts block `B` after `A`
- **THEN** both changes are visible together

#### Scenario: Failing operation rolls back the batch
- **WHEN** a batch's first operation is valid and its second is rejected
- **THEN** neither operation is applied and the error reports index 1
