## MODIFIED Requirements

### Requirement: MCP server for agents
A stdio MCP server in `mcp/` SHALL expose the agent API as tools — `list_projects`, `create_project`, `list_tasks`, `create_task`, `get_task`, `read_description`, `list_comments`, `list_references`, `transition`, `comment`, `append_description`, `list_findings`, `add_finding`, `edit_finding`, `delete_finding`, `search_pages`, `read_page`, `read_page_asset`, `create_page`, `suggest`, `suggest_action`, `list_suggestions`, `get_suggestion`, `revise_suggestion`, `withdraw_suggestion`, `get_markdown_guide` — with parameters matching the API's requests (`read_page` and `read_description` taking `anchors`). It SHALL be configured by `APP_URL` and `AGENT_TOKEN` (the agent's own token, which decides its name), and send the token with every call; `AGENT_NAME` SHALL be ignored when set. Each tool's description SHALL state what it returns, its defaults and caps, and how to ask for more; `add_finding`'s description SHALL say that findings record an exploration's results, are added without approval, and that an agent may edit and delete only its own; `suggest`'s description SHALL say to read with `anchors: true` first to get block IDs, and that a human approves or rejects every suggestion; `suggest_action`'s description SHALL list what can be suggested (renaming or deleting a project, page or task, a chore's schedule, and the ending transitions) and say that a human approves or rejects it; `list_suggestions`'s description SHALL say it lists only the agent's own open suggestions and that `changes_requested` ones have feedback to read with `get_suggestion`; `revise_suggestion`'s description SHALL say it changes the same suggestion in place, which fields fit which action, and to withdraw and suggest again to change the action, target or subject; the `suggest` description SHALL explain that a replacement retains the target’s nested blocks under the first proposed block, or after the proposed blocks if the first cannot hold them, and that tables are replaced whole; every tool that takes Markdown SHALL point to `get_markdown_guide` and say that unsupported Markdown comes back as `warnings`. `read_page_asset`'s description SHALL say it returns an uploaded image listed in `assets` by `read_page` or `read_description`, that external image URLs are never fetched, and which formats come back. Tool results SHALL be the API's response, compact (no added fields, no pretty-printing), except `read_page_asset`, whose result SHALL be the image as MCP image content (its bytes and MIME type) followed by a text item with the API's response without `data`; API errors SHALL come back as tool errors with the API's code and message.

#### Scenario: What a replacement keeps
- **WHEN** an agent reads the `suggest` description
- **THEN** it explains where retained nested blocks go and says not to repeat them
