## Context

Content is a tree of typed blocks with linked-list sibling order, changed only through batches of `insert`, `update`, `move` and `delete` operations (`BlockService.apply`), with protection hooks per owner kind. IDs are generated by the caller, so a client can create a block and keep working with it before it's saved. Pages render read-only on the server from a view model (`app/blocks/`). Comment bodies can only change through `CommentService`, which is why comments are a separate change.

Exploration settled on **one editable area per block** (Notion's model) instead of a single document editor mapped onto blocks: our model already is Notion's, so there is one source of truth and no conversion layer. The cost is owning the keyboard behavior between blocks, which this design keeps in pure, testable code.

## Goals / Non-Goals

**Goals:**
- Layers 1–3 (content, type function, structure) for every block type, on pages, project home pages and task bodies.
- Edits feel instant and are never lost silently.
- Everything except DOM glue is tested in Vitest without a browser.

**Non-Goals:**
- Block selection, slash menu, `@` references, turn-into control, comments, rich clipboard (see the proposal).

## Decisions

### 1. Three layers: editor state, DOM glue, server
```
src/editor/              pure TypeScript, no React, no DOM
  rich-text.ts           insert/delete text, toggle marks, split/join spans at offsets
  block-types.ts         defineBlockType: text?, onEnter, onEnterEmpty, onBackspaceAtStart
  editor-state.ts        blocks by id, children order, selection, version
  commands.ts            command(state, args) → { ops: Operation[], selection }
  inverse.ts             inverse of a batch, computed against the state before it
  history.ts             undo/redo stacks with typing coalescing
  save-queue.ts          coalesces updates, one request in flight, retry, ordering
app/editor/              React + DOM
  page-editor.tsx        title + blocks, keyboard and beforeinput handling
  editable-block.tsx     one contenteditable per text block, caret restore
  dom-caret.ts           DOM selection ↔ (blockId, offset), line detection, point → offset
app/lib/page-edit.server.ts   apply an edit batch to a page; delete a page
```
`src/editor/` sits in the "editor state" layer from the project's layering: it may import domain types (`Operation`, `Block`, `RichText`) but not `app/` or React. It is client code, so it never imports services.

### 2. The DOM is never the source of truth
Each text block is a `contenteditable` rendering its spans. `beforeinput` events (`insertText`, `insertReplacementText`, `deleteContentBackward`/`Forward`, `deleteWordBackward`…, `insertParagraph`, `insertLineBreak`, `formatBold`…, `historyUndo`/`Redo`) are cancelled and turned into commands; the block re-renders from state and the caret is restored from `(blockId, offset)`. `keydown` handles Enter, Backspace/Delete at edges, Tab, arrows at line edges and shortcuts, before `beforeinput`.

**Composition (IME, dead keys)** can't be cancelled: while composing, the browser owns the DOM. On `compositionend` the block's text is read back from the DOM once, diffed against the state as one `insertText`, and the block re-rendered. A block doesn't re-render from state while composing.

A block component re-renders only when its block's version changes, so React never reconciles text nodes under the user's caret mid-keystroke.

### 3. Positions are plain-text offsets
A caret is `{ blockId, offset }` and a text selection `{ blockId, anchor, focus }` within one block, offsets counted in the block's plain text (spans are flat, so this is exact). Selections spanning blocks are left to the browser in v0 (typing over them is limited to one block; that is the block-selection layer's job later). `dom-caret.ts` maps offsets to DOM positions by walking text nodes; line breaks are `\n` in span text and rendered as `<br>`.

### 4. Block types declare behavior
`src/editor/block-types.ts` mirrors `defineKind`: one declaration per type (text or not, Enter, Enter when empty, Backspace at start, whether it can have children, whether it can hold the caret). Commands read these; the markdown shortcut table lives next to them. Rendering stays in `app/editor/` keyed by the same type names.

### 5. Commands produce operations; undo applies inverses
Every edit is a command producing a batch of existing operations plus the next selection. The batch is applied to local state at once, its inverse (computed against the state before it) is pushed to the undo stack, and the batch is queued for saving. Undo applies the inverse as a new batch (and saves it), pushing the original to redo. Inverses:
- `insert` → `delete` of the inserted block (editor inserts never carry children)
- `delete` → `insert` of the block with its props and content at its old position; commands only delete leaf blocks (children are moved out first, in the same batch)
- `update` → `update` with the old type, props and content
- `move` → `move` back to the old parent and previous sibling

Typing in one block within ~1s of the previous keystroke merges into the same undo step (the content `update`s collapse to one inverse).

### 6. Saving: a queue of batches per page
The save queue keeps batches in order. Consecutive content-only `update`s of the same block are merged (last content wins); anything structural flushes the queue at once; otherwise it flushes ~600 ms after the last edit. One request is in flight at a time, so the server sees batches in edit order. On a network failure the batch stays at the head and is retried with backoff; on a rejection (4xx with a domain message) the queue is cleared, the reason shown, and the editor reloads the page from the server. `beforeunload` and React Router's `useBlocker` ask before leaving while the queue isn't empty.

Saves post `intent=edit` with the batch as JSON to the route of the surface (`/pages/:pageId`, `/projects/:projectId`, `/tasks/:taskId`) through a fetcher. Those routes' `shouldRevalidate` returns `false` for `intent=edit`, so a save doesn't reload the page under the editor; the shell revalidates when the batch changes the title (so navigation and breadcrumbs pick up renames).

### 7. Staying in sync with server-side changes
The loader sends the page tree with a `version` (the latest `updatedAt` in the tree). The editor keeps the version it last loaded or saved. When the loader returns a different version (after a task transition, for example) and the queue is empty, the editor resets its state from the new tree, keeping the caret if its block still exists. With unsaved edits, it keeps local state; the next save is applied on top, which is correct for a single user.

### 8. Server checks: edits stay in the page
A domain function `checkPageEdit(tree, batch)` in `src/domain/blocks/` validates an edit batch against the page's tree loaded without sub-page interiors: every touched or parent block belongs to the page's own content; no `delete` of a `page` block; no change to the page block except its `content` (the title); no inserted `page` or `comment` blocks. `applyPageEdit(services, pageId, batch)` checks scope (browsable page, project home, or task body depending on the route), then `blocks.apply` within the existing protection hooks. Batches are parsed with the domain's operation schema before checking.

### 9. Server render first, editor after hydration
The routes keep rendering the read-only view on the server. After hydration the page swaps to the editor built from the same tree (shared layout and typography, so nothing jumps). Toggles start open in both, so the read-only render (always expanded) matches.

### 10. Arrows across lines
On ↑/↓, the caret's client rect is compared with the first/last line of the block (from `Range.getClientRects()` of the block's content). Inside the block the browser moves the caret natively. At an edge, the target block is found in visual order (skipping blocks without text and children of closed toggles), and the caret is placed with `document.caretPositionFromPoint` (or `caretRangeFromPoint`) at the remembered x on the target's last/first line.

### 11. Deleting pages
`deletePage(services, pageId)` in `app/lib/page-edit.server.ts`: the page must be browsable and not an owned root (project home, library root); it counts the pages inside for the dialog (`pageDeletionInfo`), computes where to go (parent page, the project's library, or `/`), and applies one `delete`, which removes the subtree. The page route's action handles `intent=delete-page` and redirects. The navigation's delete actions post to `/pages/:pageId` with a fetcher, without redirecting; the shell navigates itself only when the open page is the deleted one or inside it, using the library tree it already has.

## Risks / Trade-offs

- [Browser differences in `beforeinput` and caret APIs] → Chrome and Firefox are the targets; unsupported input types fall back to reading the block's DOM once, like composition.
- [IME bugs] → composition is handled as one reconcile at the end; covered by a manual check with accented input. CJK input is not a v0 goal.
- [Losing edits] → ordered queue, retry, leave-warning, and a reload on rejection rather than silent divergence.
- [Large pages] → each block re-renders only on its own version; whole-tree work happens only on structure changes.
- [No browser automation in tests] → commands, inverses, history, queue and server checks are unit-tested; the DOM glue gets a manual checklist in the tasks, run by the user.
